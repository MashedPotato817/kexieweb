# 前端架构审计与 Vue + TypeScript + Vite 迁移评估

> 审计日期：2026-08-24
> 结论：**保持当前原生 HTML/CSS/JS 架构，不迁移**。本文件记录审计过程与结论，作为后续技术选型的决策依据，防止反复讨论。

## 1. 当前架构

单页静态站，原生 HTML/CSS/JS，无构建、无框架、无运行时依赖。

| 层 | 文件 | 规模 |
| --- | --- | --- |
| HTML | `index.html`（单页，5 个区块）+ `404.html` | 127 行 / 51 行 |
| CSS | `styles.css`（全部样式，含响应式） | 419 行 |
| JS | `script.js`（轻量交互） | 47 行 |
| 资源 | `assets/`（二维码、og 图、占位）+ `favicon.svg` | 约 10 个文件 |

内容形态：组织信息（四部门）、招新占位、资源占位、联系方式（QQ 群+二维码）直接硬编码在 `index.html`；事实登记在 `docs/kexie-mes/README.md`（维护元数据，不渲染）。

工程化：GitHub Actions 3 个（deploy + validate-site + validate-git-conventions），Ruleset 保护 main，4 项 CI 检查。无 npm、无 package.json（`.opencode/` 下的 package.json 是工具自身的，非项目依赖）。

## 2. 当前项目复杂度：低

| 维度 | 评级 | 依据 |
| --- | --- | --- |
| HTML 复杂度 | 低 | 127 行、5 区块、无嵌套业务逻辑 |
| CSS 复杂度 | 低 | 419 行、100 条规则、0 个 !important、设计变量已抽 11 个 |
| JS 复杂度 | 低 | 47 行、2 个功能（菜单 + 导航高亮 + 入场动画）、无状态管理 |
| 页面数量 | 低 | 1 个内容页 + 1 个 404 |
| 组件重复度 | 低 | 4 个部门卡片（结构相同）、3 个资源卡（空态），但规模小 |
| 状态复杂度 | 低 | 无跨组件共享状态 |
| 数据复杂度 | 低 | 事实登记在 docs，页面少量硬编码 |
| API 需求 | 低 | 无（静态站） |
| 用户交互复杂度 | 低 | 菜单开关、滚动高亮、入场动画 |
| 后续扩展需求 | 低-中 | roadmap 显示：活动/成果区、深色模式、招新资料（都小） |
| 多人协作复杂度 | 低 | 单维护者 + AI 协作，已规范化 |
| Agent 协作复杂度 | 中 | 治理体系（脚本+CI+文档）比网站本体重 |

结论：整体低复杂度。治理层（scripts/CI/文档）是仓库里「最重」的部分，但它服务的是 AI 协作而非网站功能。

## 3. 当前主要技术债

1. **内容硬编码在 HTML**：部门、联系方式直接写在 `index.html`，与登记处 `docs/kexie-mes/README.md` 是双写（改群号要改两处，靠 CI 校验强制同步）。
2. **CSS 单文件 419 行**：按功能可分块（base/nav/hero/cards），但当前规模未造成维护困难。
3. **JS 单文件**：3 个功能挤在一起，但仅 47 行，无实际问题。
4. **重复结构**：4 个部门卡片 + 3 个资源卡是重复的 HTML 片段（无模板/组件抽象）。
5. **治理体系相对网站偏重**：7 个脚本 + 4 项 CI + 多份文档（已做去 AI 依赖精简，仍略重）。

## 4. 当前最值得优化的 5 个问题（按收益排序）

1. **内容双写**（HTML ↔ docs 登记处）——最高收益。改一次群号要改两处，靠校验兜底。
2. **数据可读性**：部门/资源硬编码在 HTML 深处，非维护者不易找到；但数据量小，JSON 化收益低（roadmap 已评估不采纳）。
3. **CSS 文件组织**：单文件可拆分为 base/layout/components，但纯属整洁，非阻塞。
4. **JS 模块化**：47 行无需拆，保持现状。
5. **重复卡片模板**：如未来资源卡增长（>5 张），可考虑模板化。

关键：这些都不是「框架能救的病」——它们是数据组织和文件拆分问题，原生方案可低成本解决。

## 5. 是否需要 Vue：暂时不需要

- 当前没有 Vue 要解决的典型问题：无复杂状态、无动态列表管理、无跨页面共享状态、无大量 DOM 手动操作、无组件通信。
- 47 行 JS 完全够用，尚无「JS 在承担框架的活」。
- 引入 Vue = 引入构建、依赖、node_modules、学习成本，对单页官网是净增复杂度。
- roadmap 已有明确结论：数据 JSON 化暂不采纳（理由：破坏 file:// 双击预览、内容依赖 JS、数据量小）。

Vue 的收益什么时候会出现：活动/项目卡片 ≥ 10 张、出现真实动态数据管理需求、或需要多页面。当前未到。

## 6. 是否需要 TypeScript：不需要

- 数据结构极简单（4 部门卡片、3 资源卡、1 联系方式），无复杂对象嵌套、无 API 数据、无 undefined/null 高风险。
- 类型错误不是当前维护成本来源。
- 引入 TS = 构建 + 配置 + 学习成本，纯负担。

## 7. 是否需要 Vite：不需要

Vite 解决的是：模块打包、开发服务器 + HMR、生产构建优化、tree-shaking、自动 assets 处理、代码分割。这些只有当项目有大量 ES 模块、`.vue`/`.ts` 文件、npm 依赖时才需要。

当前项目无 npm 依赖、无模块、无构建需求，`file://` 双击即开是设计特性。引入 Vite 会破坏这个特性（构建产物无法 file:// 打开）。

CSS 文件长不是引入 Vite 的理由——CSS 拆分用普通文件分割即可，无需构建。

## 8. 是否需要 Backend / Database：不需要

- 当前「招新用第三方表单」方案完全合理：无登录、无报名状态管理、无数据查询需求。
- 活动/部门/资料是低频更新的静态信息，GitHub 仓库就是数据源。
- 只有当出现：自己管理报名数据、权限系统、实时活动列表、大量查询时，才需要评估后端。当前明确不需要。

## 9. 推荐架构：Option 1（保持当前架构）+ 轻量组织优化

保留原生 HTML/CSS/JS，不迁移。可选的轻量优化（非迁移，纯整理）：

```text
assets/
├── downloads/     # 活动资料
├── images/        # 图片
├── qrs/           # 二维码
├── logos/         # 征集投稿（gitignore）
scripts/
├── validate-site.ps1      # CI 校验
├── make-qr.py             # 二维码工具
styles.css                 # 单文件（可拆，非必须）
script.js                  # 单文件（47 行无需拆）
index.html                 # 单页
```

如果未来 CSS 增长，可拆但不引入构建：

```text
styles/           # 用 <link> 多个引入，或 @import（纯静态，无构建）
├── base.css
├── layout.css
├── components.css
```

但这不是必须的，419 行 CSS 尚在可维护范围。

## 10. 推荐迁移路线：不迁移，仅「按需轻整理」

风险最低、收益最高的顺序（都是可逆的小改动）：

1. 保持现状（当前一切可工作，file:// 预览可用）。
2. 未来内容增长时（>10 卡片）才考虑：把资源/部门改为模板渲染（JS 数组或极简模板）。
3. 未来 CSS 超 500 行且难定位时：拆分为多文件，用 `<link>` 平铺引入（无构建）。
4. 除非出现真实动态数据需求，才评估 Vue/Vite/TS。

## 11. 暂时不要做什么

- 不要引入 Vue/Vite/TS（无对应真实问题，且破坏 file:// 预览）。
- 不要做数据 JSON 化 + fetch（roadmap 已否决：破坏双击预览、依赖 JS、数据量小）。
- 不要加后端/数据库（招新用第三方表单足够）。
- 不要引入 npm 依赖或 package.json（项目定位「无构建、双击即开」）。
- 不要为了「现代感」加状态管理/组件库（纯增复杂度）。

## 12. 最终建议

保持原生架构不动，把精力放在内容本身——等待 Logo 征选结果、真实招新信息与活动资料到位后，用现有流程更新页面内容（活动/成果展示区、招新落地）。同时落实 roadmap 的季度断网演习，验证纯人维护路径。只有当活动/项目卡片显著增长或出现真实动态管理需求时，才重新评估 Vue；在那之前，原生方案低成本、零风险、完全够用。
